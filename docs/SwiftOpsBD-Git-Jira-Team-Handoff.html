Contribution integrity rule

Do not copy already-finished code to Yusuf's computer only so he can commit it under his name. Git authorship and Jira history should represent real work. Yusuf may receive the complete baseline, reproduce bugs, modify assigned files, add tests, improve validation, and open pull requests. Those commits are genuine and defensible in a faculty review.

Do not invent fifty empty or meaningless commits. The plan below contains more than fifty possible logical checkpoints; use a checkpoint only when its staged diff is coherent and testable.

3. Do not start with the ZIP

  1. Usrat organizes, tests, commits and pushes the current local baseline.
  2. Yusuf clones the two GitHub repositories normally.
  3. Yusuf creates one branch per assigned Jira task.
  4. The ZIP may be opened separately only to compare a missing asset. Never copy .git, .env, node_modules, dist, uploads, or credential JSON.
  5. Yusuf makes actual debugging/test changes and pushes his branch.
  6. Usrat reviews and merges the pull request. Jira receives the PR/test link.

8. Conflict-safe merge order

  1. Usrat finishes and pushes the backend baseline.
  2. Yusuf creates branches from that pushed commit—not from an older ZIP.
  3. Merge CAR-73 first because environment behavior affects later tests.
  4. Merge CAR-74 next, then CAR-88, CAR-78, and finally CAR-89 regression coverage.
  5. Before every pull request merge, run backend lint and the complete test suite.
  6. After backend deployment passes, publish/merge the frontend and run the end-to-end checklist.

If Yusuf's branch becomes behind:

git fetch origin
git switch debug/CAR-74-auth-roles
git rebase origin/main
# Resolve only known conflicts
git add <resolved-files>
git rebase --continue
npm test
git push --force-with-lease

Use --force-with-lease only on Yusuf's own feature branch, never on main or develop.

9. Files that must never be committed

  • .env and .env.local
  • Firebase service-account JSON
  • Stripe secret key or webhook secret
  • Supabase secret/service-role key
  • Barikoi private key where applicable
  • node_modules/, dist/, uploads/
  • Downloaded production documents, NIDs, licenses or medical files

10. Jira completion evidence

Each completed Jira item should include:

  • Commit or pull-request URL
  • Short technical summary
  • Test command and passing output
  • Screenshot or API response for user-visible behavior
  • Reviewer name
  • Deployment link when relevant

11. Final deployment checklist

  • Render watches backend main
  • Vercel watches the intended production branch
  • Render CLIENT_ORIGIN includes the Vercel origin
  • Vercel VITE_API_BASE_URL points to the public Render API
  • Firebase authorized domains include the Vercel domain
  • Stripe webhook points to the Render payment webhook endpoint
  • Supabase URL, secret and private bucket are configured on Render
  • Backend health and Swagger endpoints respond
  • Client deposit → admin matching → caregiver acceptance works
  • Clock-in/out updates admin live operations and client attendance
  • Payout, payslip and finance totals reconcile
